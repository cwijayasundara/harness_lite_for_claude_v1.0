Part oneThe AI-native SDLC

Page one · the shift

Code stopped being the bottleneck

For thirty years the software lifecycle was shaped around one assumption: writing the code is the slow part. Workshops, handoffs, and review queues were cheap next to it, so the process spent them freely.

Agents broke the assumption. A change that took four days takes forty minutes — and nothing around it speeds up to match. The planning meeting, the spec that lives in someone's head, the review queue: they stay at human speed, and become the delay.

Anthropic's AI-native SDLC playbook starts exactly there. When the build phase runs faster than the lifecycle was designed for, the bottleneck moves to the steps on either side of it: deciding what to build, and deciding whether to trust what came back.

Page two · the six stages

Every stage ends by committing a file

The playbook keeps six stages — Plan, Design, Build, Test, Deploy, Maintain — but changes what a stage is. A stage is no longer a meeting or a phase on a chart. It is a version-controlled artifact that the next stage reads as its input.

That is what makes the lifecycle machine-actionable. An agent cannot attend a workshop, but it can read spec.md and be held to it.

“Every stage commits an artifact the next stage can read. Together, the intent, the spec, the plan, the diff and the review findings are the audit trail.” The AI-native SDLC playbook

Page three · what steers the agent

Advice it can ignore. Guards it cannot.

An agent is steered by whatever is in front of it, so the playbook makes institutional knowledge a checked-in asset instead of tribal memory. Most of these are advisory. One of them is not, and the difference matters.

CLAUDE.md

Under one page, read at the start of every session: conventions, commands, architecture, and the mistakes this project actually makes.

Skills

Version-controlled policy — security, compliance, brand, UX — that triggers when the work touches it. Advisory, and narrow on purpose.

Hooks

Deterministic. They allow, ask, or block an action as it happens. This is the only layer that can actually stop the agent.

Evals

A regression suite for the agent's own configuration — re-run whenever a skill, a hook, or CLAUDE.md changes.

Feedback loops

Claude checks its own work before handing it over: tests, builds, screenshots. Cheap proof beats a confident summary.

Subagents & worktrees

Scoped helpers for repeated jobs, and parallel sessions so one engineer can steer several changes at once.

Review changes shape too. Line-by-line human reading does not survive contact with agent throughput, so review becomes layered: automated checks first, agentic review next, and human attention spent on intent and risk rather than syntax.

Page four · the loop closes

Three levels of automation, one level of judgement

The playbook does not ask you to arrive fully autonomous. It describes a progression, and the honest position is knowing which rung you are standing on.

1 · Manual triggering

An engineer runs each stage by hand and commits the artifact. The chain exists; a person moves it along.

2 · Automated handover

An accepted artifact triggers the next stage through CI. Approval, not attention, is what moves the work forward.

3 · Autonomous loop

Monitoring breaches a control band, Claude diagnoses it and writes a new intent.md, and the finding re-enters the pipeline without a human starting it.

Autonomy is bounded by environment rather than by trust: an agent acts freely in development, uses pre-approved runbooks in staging, and needs release-manager authorization for the live system — enforced by a hook, not by a policy document.

And it is measured at the handoffs, not by lines of code. Leading indicators: time from first conversation to a committed intent, share of changes merged on the first implementation pass, time to first review, time from a control-band breach to an intent in the triage queue. Lagging indicators: rework cycles, change failure rate, escaped defects, repeat incidents.

“The loop keeps running. Human judgement stays above it.” The AI-native SDLC playbook

Part twoHow lean v1 implements it

Page five · the mapping

The chain adopted verbatim. The ceremony, not.

This harness takes the artifact chain literally — every stage commits a file the next stage reads, and git is the audit trail — and refuses almost everything built around it. No conductor command per phase, no autonomy modes, no ungated loop. Twelve skills, three subagents, five hook bindings, one CLI.

Here is the whole mapping, stage by stage.

Playbook stageIn lean v1Human gate
1 · Planintent.md The intent skill writes .claude/artifacts/intent/<slug>.md — problem, outcome, constraints, and the questions that block progress. —
2 · Designspec.md The spec skill turns an approved intent into numbered testable behaviours, explicit out-of-scope, domain vocabulary, and flagged policy concerns. GATE 1 · spec approved
3 · Buildplan.md → diff plan names the exact files and the proof for each behaviour; implement works in red-green slices. Five hooks and three agents run underneath. GATE 2 · plan approved
4 · Testevidence harness check stages (fast / stop / commit) plus evals/tasks.json in CI. harness status reports the latest eval pass rate. —
5 · DeployPR + findings The review skill writes a severity-ranked review artifact; CI and branch protection are the gate; harness handoff opens the next-stage draft PR. GATE 3 · review approved / merged
6 · Maintainincident.md A scheduled harness monitor detect compares metrics to numeric bands and writes an incident plus a new intent. The metric collector is yours to supply. service owner triage

Page six · the honest boundary

Core implementation, or adapter contract — say which

Stages one to four run inside this repository today, on a cold clone, with nothing to install. Stages five and six have schemas, validation, and gates — but they only become operational once a project supplies its own source control, release path, rollback, and metric sources.

The rule the harness holds itself to: do not describe a template as automation, and do not describe an uncommitted approval as a passed gate.

Page seven · fidelity

Followed exactly, diverged deliberately

The chain, as written

intent.md → spec.md → plan.md → diff as version-controlled handoffs, under one stable change slug.

CLAUDE.md under a page

Commands, conventions, and things this project gets wrong — a line added the second time a mistake happens, never the first.

Verification before “done”

No completion claim without the pasted output of harness check --stage stop.

Separation of duties

The verifier agent has Bash so it can run the checks, and no Write so it cannot make them pass. Enforced by contract, not by prose.

Where we diverge, and why

Approval hooks inside Build

Gates only at spec, plan, and merge. An approval pause inside the build loop destroys the parallelism agents are for — the playbook says so itself.

Managed settings and certification

A template plus harness doctor --enterprise. Real enforcement is MDM or an admin console; a git-tracked settings.json is not policy.

Anomaly detection by model

harness monitor detect uses numeric 1σ / 2σ / 3σ bands. Detection stays model-free; 2σ diagnoses, 3σ writes an intent and may roll staging back.

Skills up to 500 lines

A 130-line hard stop, around 80 in practice. Short skills trigger better, and control flow belongs in the CLI rather than in a numbered list inside a skill.

Artifacts in repo-root docs/

Artifacts live under .claude/artifacts/: one directory to copy between repos, one place an agent looks. Prose about the harness — including this page — sits in the repo's own docs/, since init never installs it into your project.

Page eight · what it measures

Indicators out of git, not out of a dashboard

harness status computes the playbook's leading indicators from commit history: intent survival (accepted versus closed), mean hours to a committed intent, spec commits after the first plan commit, first-pass review share, and the latest eval pass rate. A missing clock prints unmeasured — never a fabricated zero.

Underneath sits the one control the playbook does not describe, and that this harness treats as control number one: the ledger. Every sensor invocation is recorded, and harness ledger audit decides monthly which controls have earned their place. It has no off switch — including for the harness's own development.

Part threeWhat it feels like to use

The whole idea

A robot builder, and a site inspector

You ask for something in normal words. Claude builds it. The harness inspects every change and hands it back until it passes. Then a human says yes.

Three moving parts

Help before. Alarms after. A logbook that judges both.

Guides

Notes handed to Claude before it types: house rules, how-to cards, a map of your code.

Sensors

Automatic checks run after it types: tests, secret scanner, a second Claude that reviews the diff.

The logbook

Every check writes down what it did. Checks that never catch anything get deleted.

The paper trail

Nobody writes code first

Every change walks the same five steps, and each step is a small file saved in your repo. You can read them. You can reject them.

01

intent

What hurts, and what "better" would look like. No solutions yet.

02

spec

A numbered list of things it must do — each one testable. Plus what it will not do.

03

plan

The exact list of files that will change. If the code touches a file the plan never named, the build stops.

04

code

Small slices. Failing test first, then the fix. Never weaken a test to make it pass.

05

review

A separate Claude reads the change against the spec and the plan, and ranks what it finds.

The tripwires

Five moments where something watches

You never trigger these. They fire on their own, five times, in five places.

The unusual part

Rules that never catch anything get fired

Most safety systems only grow. This one keeps a logbook of every check it ever ran, and once a month it deletes the ones that have never found a single problem.

earning-its-place

Objects often enough to be worth the wait. Keep.

rarely-fires

Objects, but hardly ever. Ask if a test already covers it.

candidate-for-deletion

Fifty runs, zero objections. Delete it.

unreliable

Crashes too often. A broken check is a lie — fix or delete.

insufficient-data

Too new to judge. Wait.

User guide

What you actually do

Three things: install it once, talk normally, and say yes twice.

01

Install it, once

Nothing to download and nothing to build — it is plain Node with zero dependencies.

git clone https://github.com/cwijayasundara/claude_harness_lean_v1.git
cd /path/to/your/project
node /path/to/claude_harness_lean_v1/.claude/bin/harness init --into .

Then open one file, .claude/harness.toml, and tell it how your project formats, lints, and tests. That is the only setup.

02

Ask for what you want

No slash commands. No shell. Just say it.

“Add pagination to the orders endpoint using the Lean AIDLC workflow.”

“Take docs/search-prd.md through the workflow. Pause only when you need me.”

03

Read, approve, continue

Claude stops and waits. Open the file it wrote in .claude/artifacts/, change its status to approved, commit that, and say so.

“Approved. Continue the workflow.”

Claude figures out where it left off by reading the repo, not by remembering the chat. Close the laptop mid-change and it picks up exactly where it stopped.

House rules

Small on purpose

Zero dependencies

No install step. It runs on a fresh clone of your repo with nothing but Node.

The budget is full

12 skills, 3 helper agents, 5 tripwires. Adding one means deleting one — the build enforces it.

Every rule names a bug

A check must say which real defect it prevents. No reason, no rule.

No self-exemption

The harness is developed under its own rules. If a gate is wrong here, it is wrong.

In one line: Claude builds fast, the harness makes it prove the work, and a human still signs. Want to go deeper on any part?
