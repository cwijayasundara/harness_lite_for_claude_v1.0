The Subtractive Harness

v6 isn't failing because it is big. It is big because it never had a working mechanism for removing anything. Here is the evidence, the parts worth rescuing, and a design for a harness that stays small on purpose.

01 — Diagnosis

The verdict: you built a workflow engine in prompt-space

The thing that makes v6 feel bulky is not the number of controls. It is that the majority of its code exists to make a language model follow a sequence — and a model following a sequence is the single most expensive way to implement control flow ever devised.

1,595tracked files
~195kreal text LOC
56skills
203scripts
121hook lib files
118npm scripts
180declared controls
8evals for all of it

Look at what the commits actually bought. Five overlapping change lanes (vibe, change, refactor, feature, sprint) plus two conductors (build, auto). Four independent mechanisms for keeping a long run alive: a Stop hook that returns {decision:"block"} to force the model to continue, /auto's own stopping-criteria section, a budget state machine, and a chain script that spawns fresh claude -p processes per wave. Three registries of controls that disagree with each other, plus a fourth that installs them.

None of that is a knowledge problem. It is a scheduling problem, and schedulers belong in bin/, not in markdown.

The second thing the evidence shows is more uncomfortable: the pipeline the whole design is organised around has never run. Your own installer prints it — the planning pack is 122 units with "0 spawns of generator/evaluator/planner/design-critic in 23d telemetry; no specs/brd|spec|design artifacts ever produced in this repo." The only lane with a real usage log is /vibe, with 18 entries. You have built, tested, documented and gated an SDLC pipeline that you personally route around.

The asymmetry that produced 1,000 commits

v6 has a strong additive force and a broken subtractive one. Adding a control is one PR. Removing one requires sensor-value, which needs ≥20 recorded outcomes and has zero — sensor-outcomes.jsonl was never written. So the ratchet only turns one way, and you then built a meta-ratchet (control-budget-gate.js) to cap the number of controls, a dedup tool to find overlapping ones, a runbook to adjudicate them, and a marker file to record the adjudication. The one audit that ran found: "Merges this pass: 0."

Every over-engineered system I have seen has this same shape. The fix is never "be more disciplined." It is to make deletion cheap and evidence automatic, on day one, before control number two exists.

02 — Evidence

Six structural findings

Each of these is verifiable in the repo as it stands today. Each ends with the law it should have been prevented by — those laws are collected in §05.

F1 · Control flow in prompt-space

The model was made responsible for sequencing

auto-continue-on-stop.js (174 LOC) parses claude-progress.txt with regexes, then returns {decision:'block'} to prevent the session ending, up to five consecutive no-progress turns. build/SKILL.md is 76 lines pointing at six reference files; auto/SKILL.md is 52 lines pointing at fourteen. Both then re-inline the names they just split out, under a heading called "Load-bearing names (always visible)."

The brd → brd-render, spec → spec-render, design → design-render split exists purely because a forked conductor "silently converted all four of its gated stops into prose the model read to itself." A runtime quirk has been promoted into six skills.

Law 2Skills describe how to do a thing well. They never sequence phases. Anything that decides what happens next is a script with an exit code.
F2 · No subtractive force with data behind it

The removal mechanism has never had an input

The README markets the outcome ledger as "the subtractive half of the loop: without it, no control can ever be removed." npm run sensor-value returns INSUFFICIENT DATA — 0 recorded outcome(s), need >= 20. The telemetry pack's own description concedes it: "Report-only; none of it gates. sensor-outcomes.jsonl was never written, so none of it has ever produced a decision."

Meanwhile 46 units of telemetry, an OTel collector, Prometheus, a pushgateway and three Grafana dashboards exist and are off.

Law 4The outcome ledger is control #1, not control #180. Every check appends a row on every invocation before any second control ships.
F3 · Four registries for one set of controls

The centre of gravity is a JSON file nobody can regenerate

harness-manifest.json 180 controls → docs, budget gate, wiring tests (29 commits — top churn) hooks/lib/gate-registry.js 31 gates → git pre-commit config/gate-checks.json 17 checks → /gate command config/packs.json 409 units → installers (25 commits — 2nd)

Five ids — cycle-detection, coupling-ratchet, duplication-ratchet, ownership-check, canvas-sync — appear in two of these with independent config, independent remediation strings and independent blocking semantics. The two highest-churn files in the repo are the two biggest registries. That is the signature of hand-maintained duplication.

Law 3One registry. Docs, catalogues, install manifests and the check runner are all generated from it. If two files can disagree, one of them should not exist.
F4 · Prose-consistency tests as a permanent tax

57k LOC of tests for 52k LOC of logic — but the wrong 22 files

The node:test suite is genuinely good: zero dependencies, runs green on a cold clone in under two seconds. But 22 of the 428 test files are *wiring-contract*.test.js that assert cross-file prose agreement — e.g. verifying that a gate is "reflected in HARNESS.md's Behaviour row and the 'current holes' ledger." Every rename now costs a documentation edit in three places plus a test fix.

Law 3, corollaryNever test that two prose files agree. Generate one from the other and test the generator once.
F5 · The knowledge subsystem is pointed at the wrong tree

A fresh, cheap, correct mechanism producing a wrong answer

code_index.py:61 dirnames[:] = [d for d in dirnames if d not in EXCLUDES and not d.startswith('.')] → .claude/ starts with a dot. The 48k LOC that IS the harness is invisible to the harness's own code graph.

The consequence is visible in the committed artifact. WIKI.md reports 497 modules and 2,319 edges; its top ten hubs are test/helpers/hook-fixture.js, test/helpers/skill-corpus.js, and two files from symphony_clone, a vendored sibling service. .harness/wiki.json declares priority_paths: [".claude/scripts", ".claude/hooks", ".claude/skills"] — matching nothing.

The other wiki, open_wiki/, is the only one permitted to read .claude/. Its .last-update.json says command: "init", dated 18 July, against a git head that is not in this repo's history. Eleven pages, 406 lines, never updated. The comprehensive wiki is blind; the wiki that can see is stale.

Separately: on a fresh clone code-graph.meta.json is gitignored, so the producer check fails and graph-refresh silently truncates the dirty list and returns. The graph only advances on the one machine where someone ran /code-map.

Law 7The graph is a cache that must answer five named questions. Prove it answers them with a test that asks them. If it can't, the agent falls back to grep — the graph is never a required input.
F6 · The strongest control is disabled where it runs

Self-exemption and universal fail-open

isHarnessRepo() bypasses the trust-boundary check in pre-write-gate.js, pre-bash-gate.js, artifact-guard.js and check-git-hooks.js. The harness's central thesis — agents may not modify the gates that verify their own work — is switched off in the only repository where it has ever executed. Every hook also wraps main() in try{…}catch(_){process.exit(0)}, so a broken guard is indistinguishable from a passing one.

Fail-open is the right default for a hook. Silent fail-open is not. There is no counter anywhere that says how many times a check errored.

Law 10Fail open, but log the failure to the ledger and surface the count at SessionStart. A control with no observed firings is a candidate for deletion; a control with unobserved errors is a lie.

04 — Synthesis

Where the sources agree — and where they don't

You have been reading four bodies of work that appear to reinforce each other and in two places genuinely conflict. Getting the conflicts wrong is how v6 got heavy.

The consensus (build on this without hesitation)

  • Agent = model + harness, and the harness decomposes into exactly two things: guides that steer before the agent acts, and sensors that observe after. Böckeler's taxonomy is the cleanest available and it is sufficient. You do not need a third category.
  • Artifacts are the handoff protocol; git is the audit trail. Anthropic's chain — intent.md → spec.md → plan.md → diff → review findings — is the same shape as SPDD's canvas and OpenAI's docs/ tree. Adopt the chain; the disagreement is only about how many boxes it has.
  • Repository as system of record. OpenAI: information not in the repo effectively does not exist to the agent. This is why a 100-line AGENTS.md pointing at structured docs beats a 12KB CLAUDE.md.
  • Linters that teach. Both OpenAI and Böckeler independently arrive at: error messages must carry remediation written for the agent, and must permit a justified threshold increase rather than only suppress-or-comply. Böckeler's follow-on insight is sharper than either — the exceptions the agent created are where human review should start.
  • Verification before "done", with a quantifiable target. Not "tests look fine" but "all tests in X pass, paste the output."
  • Evals on the harness config itself. Anthropic prescribes 20–50 real tasks re-run on every change to CLAUDE.md, skills or hooks. Your 8 are the seed of this.

Conflict 1 — merge gates: OpenAI removes them, the playbook adds them

OpenAI ships one million agent-written lines with minimal blocking merge gates, short-lived PRs, flakes handled by re-run rather than by blocking. Anthropic's playbook adds review passes, hook approval gates, separation of duties and release-manager sign-off. Both are correct for their context: OpenAI optimises throughput inside a seven-person team on a greenfield product; the playbook optimises auditability for regulated enterprises.

Resolution: gate by risk tier, not by taste, and make the tier a property of the change rather than of the harness. A dependency bump and a payments-path change do not deserve the same ceremony. v6 encoded this as a five-mode autonomy policy with a certification requirement and never exercised it; the lean version is three tiers and one line in plan.md.

Conflict 2 — ceremony: SPDD versus the lean-skills school

SPDD is the heaviest process in your reading list: a seven-part REASONS canvas, eight slash commands, two-way prompt↔code synchronisation, and its own honest admission that "variance between two developers writing the same Canvas remains high" and that it lacks any automated verification of canvas completeness. At the other end, pipedrive/mattpocock-skills opens by rejecting exactly that: "approaches like GSD, BMAD and Spec-Kit try to help by owning the process. But while doing so, they take away your control and make bugs in the process hard to resolve."

Resolution: ceremony is a per-change tax, and most changes are small. SPDD's own fitness table rates itself two stars for hotfixes and spikes and one star for unclear domains — which is most real work. v6 built SPDD-scale ceremony and then routed around it via /vibe, which is the empirical answer. Build the lean end and let the heavy path be opt-in for the changes that earn it.

Conflict 3 — where orchestration lives

swarm-forge answers "how do I run many agents" with N CLI processes in N git worktrees and a file-as-queue protocol. Devin and your own symphony_clone answer it with a ticket board as control plane. Both are legitimate — and both are outside the harness. The harness is what one agent runs inside one repository. Multiplying agents is a separate product with a separate lifecycle.

This is the single largest cut available to you: everything in v6 concerned with lanes, dispatch, concurrency caps, wave chaining and auto-continuation belongs to a supervisor you may or may not build later. It is not harness code.

The one piece of received wisdom to ignore

Anthropic's skill guidance permits SKILL.md up to 500 lines / 5k words. mattpocock's library — 14 published skills, none over 130 lines, median ~85 — is the better target. Treat 500 as the hard stop and 100 as the design goal. v6's skills average 268 lines including references, and the two conductors are effectively 1,000 and 1,850 lines. That is the difference between a skill and a program written in English.

05 — Constitution

Ten laws for lean_v1

Put these in docs/CONSTITUTION.md and make three of them mechanically enforced (2, 5, 9). The rest are review criteria.

LAW 01

Guides and sensors, nothing else

If a component is not steering the agent before it acts or observing it after, it is not part of the harness. This deletes lanes, conductors, autonomy tiers and certification profiles on contact.

LAW 02

Control flow is a script

Anything that decides what happens next is a CLI with an exit code. Skills describe how to do one thing well and never sequence phases. Enforced: a test fails if any SKILL.md contains a numbered phase list longer than three steps.

LAW 03

One registry, everything generated

harness.toml is the only hand-edited source of truth. The check catalogue, the docs table, the hook bindings and the install manifest are all generated from it. If two files can disagree, delete one.

LAW 04

The ledger is control #1

.harness/ledger.jsonl exists before the second control does. Every check invocation appends {control, stage, verdict, ms, changed_files}. No exceptions, no sampling, no opt-in telemetry stack.

LAW 05

Hard budgets, enforced by a test

≤12 skills · ≤5 hook bindings · ≤3 subagents · ≤600 LOC of hook code · ≤120 lines in CLAUDE.md. The build fails when exceeded. You cannot argue with a red test; you must delete something.

LAW 06

Capability verbs, not packs

Language support is eight commands in a TOML table, not a plugin system. Adding Rust is eight lines. v6's nine packs, four profiles, partition checker and accepted-edge ledger all exist to solve a problem this makes disappear.

LAW 07

The graph is a cache with a miss path

It must answer five named questions, proven by a test that asks them. It indexes everything, dotdirs included. When it is stale or absent the agent falls back to grep and says so. Never a required input.

LAW 08

Three human gates, no more

Spec approved · plan approved · PR merged. Everything else is advisory output the human may read. Approval pauses inside the build loop destroy the parallelism that makes agents worth running.

LAW 09

Evals before controls

Twenty golden tasks with deterministic assertions and per-task budgets exist before skill #13 or hook #6. Every incident becomes a permanent eval. Enforced: CI runs the suite on any diff touching .claude/** or checks/**.

LAW 10

Every control carries its defect

A required why: field naming the incident or eval it prevents, plus a link to the ledger query that shows it firing. No why, or no firings in 50 sessions with zero true positives — it goes at the next audit.

06 — Design

Reference architecture

Target: under 40 committed files and under 4,000 lines of harness code, excluding evals and fixtures. If it grows past that without ledger evidence, something is wrong.

The five hooks — and only five

All five bind to one binary. There is no hooks/lib/ with 121 files; there are four check modules and a dispatcher. Where Anthropic's reference supports a prompt-based hook (Stop, SubagentStop, UserPromptSubmit, PreToolUse), prefer it over a script.

The discipline five are exactly the answer to your team problem — people who lean entirely on the agent and are not grounded in TDD, SOLID or refactoring. They work because they are short enough to fire reliably and narrow enough to be unambiguous. This is where "engineering best practice" gets encoded; not in a 900-line conductor.

Three subagents, each with a contract

  • explorer — Read, Grep, Glob. Answers "where is X" without polluting the main context. Cannot write.
  • verifier — Read, Bash. Runs the app, runs the checks, reports. Cannot write source. This is the writer/grader separation, enforced by verifier.contract.json, not by prose.
  • reviewer — Read, Grep, Glob. Diff review against spec and plan.

v6 has ten agents; six of them have never been spawned. Three is enough until the ledger says otherwise.

07 — Portability

Language independence in eight verbs

This is the design decision that makes "any programming language or framework" tractable. v6 solved it with nine packs, four profiles, a partition checker, an accepted-edge ledger and a 614-line packs.json. The lean answer is a table.

[project]
name    = "acme-payments"
tiers   = ["low", "standard", "critical"]   # risk tiers from plan.md

[capabilities]                 # the 8 verbs. Empty string = not available.
fmt       = "uv run ruff format {files}"
lint      = "uv run ruff check --output-format=json {files}"
typecheck = "uv run mypy --output json {files}"
test      = "uv run pytest -q --json-report"
coverage  = "uv run pytest --cov --cov-report=json"
arch      = "uv run import-linter --output json"
secrets   = "gitleaks detect --report-format json --no-git"
deps      = "uv pip list --outdated --format json"

[stages]                       # which verbs run when
fast   = ["fmt", "lint", "typecheck"]
stop   = ["fast", "test"]
commit = ["stop", "arch", "secrets"]
drift  = ["coverage", "deps"]  # scheduled, never blocking

[graph]
include = [".", ".claude"]     # dotdirs indexed. F5 does not happen again.
exclude = ["node_modules", ".venv", "dist", "target"]

[budget]
subagent_context_soft = 140000
subagent_context_hard = 200000
change_cost_ceiling   = 4.00   # USD, ratcheted from .harness/baseline.json

harness.toml — the whole of language support. A TypeScript project swaps eight strings.

Three properties make this work where a plugin system doesn't:

  • Every verb is optional. A missing arch command means the arch sensor reports skipped, not failed. Coverage grows with the project rather than being a precondition.
  • Every verb emits JSON, normalised by the runner. One schema — {control, verdict, findings:[{file, line, rule, message, fix}]} — regardless of whether it came from ruff, eslint, clippy or golangci-lint. The agent learns one output format for every language it will ever touch. This is the single highest-leverage line in the design.
  • Remediation is attached at the runner, not the tool. Where a native tool's message is unhelpful to an agent, harness.toml carries a per-rule override that appends the fix and the permitted escape hatch ("suppress with a justification comment, or raise the threshold in harness.toml and say why"). Böckeler's finding — allow a justified threshold increase, then review the exceptions — is worth more than any individual rule.
On the PRD-to-code predictability you're after

Predictability does not come from a longer spec. It comes from the diff being checkable against the plan. Make plan.md name the files it will touch, and add one check — plan-drift — that compares the diff's file list against the plan's. When they disagree, the agent must either update the plan in the same commit or explain. That one sensor buys more determinism than the entire REASONS canvas, and costs about 40 lines.

08 — Economics

Token strategy: five moves, measured

v6 has roughly a ten-control token governor and its own installer reports that it "false-blocked 3× in one session." Fewer, sharper moves:

  1. Context ceiling on subagent writes. Port context-ceiling.js unchanged. Soft warning at 140k, hard block at 200k, writes only, handoff notes exempt. This is the one control in v6 with a measured dollar figure behind it.
  2. Budgeted context packs instead of file reads. harness pack "<question>" returns ~1,200 tokens of file:line-range slices from the graph rather than whole files. Ship it with a benchmark of golden queries scoring recall against naive full-file reads, so the saving is a number rather than a belief.
  3. Normalised JSON check output, truncated. Sensor output is the second-biggest token sink after file reads. Cap findings at 20 per control, write the full report to .harness/last-check.json, and give the agent the path.
  4. Prompt-cache prefix stability. Block mid-session writes to CLAUDE.md, .mcp.json and settings. v6 got this right and it is not widely known — a single edit to the cached prefix invalidates the cache for the rest of the session.
  5. A cost ratchet with a real baseline. Port the sprint1-baseline.json idea: per-stage output tokens and USD for one reference change, checked into the repo, compared on every eval run. A regression in token efficiency should fail CI exactly like a regression in tests.

Note what is not on this list: compress-cache-retrieve, a navigation index with six sub-tools, per-phase cost trackers, and a token advisor that blocks greps. Those are v6's answer to a context problem largely created by its own orchestration overhead. Remove the overhead first and measure again.

09 — Knowledge

Graph and wiki, done cheaply

Your requirement — a code graph and wiki that stay in sync with code changes — is correct and v6's mechanism for it is good. Only the target and the ambition need fixing.

One producer

Tree-sitter, multi-language, vendored wheels. v6 defines a five-tier producer ladder (AST → SCIP → Understand → Graphify → regex) of which exactly one has ever run, with test files for adapters that have no users. Delete the ladder.

Five questions, proven by a test

The graph exists to answer: who calls this · what does this call · what are the hubs · what cycles exist · what changed under this symbol since <ref>. Write an integration test that asks all five against a fixture repo and asserts specific answers. If a question cannot be answered, the graph is not done; if a query is not one of the five, it is not built.

Sync via the pattern you already have

PostToolUse appends the path to a dirty list; Stop coalesces and re-indexes under a TTL lock; failures stamp STALE since <ts> at the top of the rendered output rather than failing silently. Sub-second, zero LLM tokens. Add the one thing v6 lacks: on a fresh clone with no graph, build it rather than returning quietly.

The wiki is for the agent first

Deterministic, LLM-free, rendered from the graph, gitignored. Per-cluster markdown pages of 30–200 lines that can be read individually, plus the query CLI. Do not commit a 380KB HTML browser — v6 pays a ~600KB regenerated diff on a tenth of its commits for a viewer no agent uses. If humans want a browser, generate it on demand into .harness/.

Leave the LLM-generated wiki out of v1 entirely. v6's ran once, in July, and was never updated; the daily workflow that would have refreshed it opens PRs nobody merges. An LLM wiki is a monthly artefact at best, and it is not what keeps a graph in sync.

10 — Regression

Evals are the ratchet that lets you delete

This is the mechanism v6 is missing and the reason it can only grow. With a real eval suite, removing a control is safe: delete it, run the suite, and if nothing regresses it was not doing anything. Without one, every control is load-bearing by default and the count only rises.

Start with the eight v6 already has — they test exactly the right behaviours — and grow to twenty before you write skill thirteen.

Three implementation notes, all learnable from what you already built: inject the invoker so the runner itself is unit-tested without a model; give every task a USD ceiling and a timeout; exit 0 cleanly when no API key is present so the suite never blocks a contributor. Add one thing v6 lacks — run the eight highest-signal tasks three times each and report variance, because a 2-of-3 pass is a different finding from a 3-of-3.

CI trigger: any diff touching .claude/**, checks/**, or harness.toml. That is the whole governance model. It replaces certification profiles, autonomy tiers and the control-budget gate.

11 — Execution

Five weeks to a harness you'd trust

Sequenced so that each phase is independently useful and the whole thing is abandonable at any point without waste.

Week 1

Walking skeleton

harness.toml with eight verbs for one language. bin/harness check with the normalised JSON schema. Three checks (fmt, lint, test). One hook: PostToolUse. The ledger, writing from the first invocation.

Exit criterion: you make one real change in one real repository, and ledger.jsonl has rows in it. Nothing else ships until that is true.

Week 2

The artifact chain and the guards

Four chain skills (intent, spec, plan, implement), the two write guards, three agent contracts, CLAUDE.md under 120 lines. The plan-drift check.

Exit criterion: a PRD goes to a merged PR through the chain, and the diff's file list matches the plan.

Week 3

Evals, then freeze

Port the eight v6 tasks, add twelve. Wire CI on .claude/** · checks/** · harness.toml. Add the budget test that enforces Law 5.

Exit criterion: the suite is green, and the budget test fails when you deliberately add a thirteenth skill. From here the counts cannot grow without deletion.

Week 4

Graph, wiki, context packs

Single tree-sitter producer indexing dotdirs. Five-question test. Dirty-list/coalesce sync. harness pack with the recall benchmark. The map skill.

Exit criterion: the pack benchmark shows a measured token reduction against the week-2 baseline. If it doesn't, the graph is a cache miss and you cut it.

Week 5

Second language, then discipline skills

Add a second language by writing eight strings — this is the test of Law 6. Then the five discipline skills, and only then look at the ledger to decide what control #6 should be.

Exit criterion: a Python repo and a TypeScript repo run the same harness with no code differences.

Ongoing

Earn controls back from data

Monthly: query the ledger. Any control with a fire rate under 5% over 50 sessions and zero true positives is deleted. Any recurring review finding becomes a CLAUDE.md line first, a check second, and a skill only if the first two fail. Every production incident becomes an eval, permanently.

Explicitly not in v1

Each of these consumed real effort in v6 and returned nothing measurable. They are not forbidden forever; they are forbidden until the ledger asks for them.

  • Conductor skills
  • Auto-continue hooks
  • Concurrency gates
  • Autonomy tiers
  • Certification profiles
  • Pack / profile installer
  • Partition checker
  • Control-budget meta-ratchet
  • Dedup audit tooling

12 — Governance

Instrumentation and kill criteria

Four numbers, all derivable from the ledger and the eval suite. No dashboard stack required — harness ledger report prints them.

MetricDefinitionWhat it tells you
First-pass merge rateShare of changes merged from the first implementation attemptWhether the guides are working. Rising = spec and plan quality improving.
Tokens per merged changeOutput tokens and USD, against the checked-in baselineYour explicit goal, as a ratchet. A rise is a regression, not a cost of doing business.
Sensor precisionPer control: fired ÷ (fired + would-have-been-caught-later), from ledger + review findingsWhich controls to delete. This is the number v6 never had.
Eval pass rateSuite result on every config change, with variance on the top eightWhether a harness edit made things better or only different.

Kill criteria — write these down before you need them

  • A control dies at fire rate <5% over 50 sessions with zero true positives, or when deleting it does not move the eval suite.
  • A skill dies when it has not been invoked in 30 days, or when its content could be three lines in CLAUDE.md.
  • A subsystem (graph, packs, wiki) dies when its own benchmark shows no measured benefit — this is why every subsystem ships with a benchmark in the same PR.
  • The harness itself is in trouble when the budget test starts requiring exemptions, when two files can disagree about the same fact, or when you find yourself routing around a lane you built. All three happened in v6 and each was visible in the repo months before it was acted on.
The one-sentence version

Build the ledger first, cap the counts with a test, put every deterministic decision behind bin/harness, keep skills under a hundred lines and describing how rather than when, and let the eval suite be the only thing that authorises growth.
